# 系统性 debug

## 1. 目的与授权边界

用于复现故障、收集证据、定位根因、提出修复方案和验证回归。仅要求“诊断、调查、解释”时默认只读，不得自行实施修复；开发者明确要求修复，且变更未触发正式方案门禁时，才可进入实施。

## 2. 前置确认

1. 读取项目 Agent、当前状态、Work Item Registry 和相关架构文档。
2. 允许开发者只描述“哪里不对、原本希望怎样”。Agent 先自行检查项目，再通过少量口语化问题补齐发生时间、操作步骤和可观察现象；不要要求开发者先提供日志、堆栈或根因。
3. Agent 负责记录平台、项目根、运行环境、版本、输入、期望行为和实际行为，并主动收集可访问的日志与错误。
4. 明确复现是否可能修改用户数据、网络状态、系统代理或本地配置；有风险时先请求授权并建立快照。
5. 将日志、堆栈、失败命令和时间条件作为证据，不把猜测写成确认事实。

## 3. 诊断流程

1. 建立最小稳定复现；无法复现时说明已尝试条件和缺失信息。
2. 缩小故障层：UI、ViewModel、Service、Model、配置生成、Xray engine、updater、构建或 vHarness 治理。
3. 比较正常与异常路径，检查最近变更、边界输入、平台差异和生成内容污染。
4. 形成候选假设，每个假设列出支持证据、反证和可区分实验。
5. 用最小只读检查或低风险实验裁决假设，输出根因与影响范围。
6. 若需要修改，判断是否触发 `SOP_change_planning.md`；触发时创建正式方案并等待 approve。

## 4. 修复与回归

1. 选择解决根因的最小修改，不用屏蔽错误、删除 Decision Item 或放宽验证器来制造通过。
2. 为根因增加可失败于修复前、通过于修复后的回归测试或等价验证。
3. 先运行定向复现，再运行相关测试；涉及发布、平台或 updater 时执行对应完整验证。
4. 验证失败立即停止，保留现场并报告恢复路径；不得连续试错掩盖新的失败。

## 5. 输出格式

- 先用白话回答：问题是什么、为什么发生、是否已修好、开发者还需要做什么。
- 症状与复现条件。
- 根因及直接证据。
- 影响范围和未受影响范围。
- 已实施修复或建议方案。
- 验证命令与结果。
- 风险、限制、恢复路径和 Decision Item。
