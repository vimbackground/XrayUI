# Agent 辅助开发通用经验

本文件保存从本项目提炼、脱敏、解耦后的通用经验，可作为未来 vHarness 项目开发和升级的候选输入。记录在此不代表已经向外部项目同步；任何外部写入必须由开发者另行批准。

## EXP-001：项目内恢复目录必须脱离构建发现机制

- 来源：本项目 Host Repository 适配复盘，2026-09-07。
- 通用问题：许多构建系统会递归发现源码或资源；把完整快照放在项目根，即使版本管理已忽略，也可能被编译或打包。
- 可复用做法：创建快照前检查构建系统的默认 glob；恢复目录同时加入版本控制排除、构建项目项排除和发布排除；创建快照后执行一次代表性构建。
- 适用条件：快照或备份保存在项目根内，且技术栈使用递归默认文件发现。
- 限制：不同构建系统的排除方式不同，不能固化某一项目文件语法。
- 建议 action：未来 vHarness recovery 工具或平台 SOP 应在环境探针中检查构建发现机制。

## EXP-002：Vibe Coding 提示词负责启动对话，SOP 负责工程约束

- 来源：本项目提示工程集复盘，2026-09-07。
- 通用问题：把范围、非目标、根因、文件清单和命令都做成必填项，会把 Agent 的工程职责转嫁给非程序员开发者。
- 可复用做法：提示词使用自然语言表达意图并允许原样复制；Agent 主动查看项目，只追问无法推导且会影响结果的事项；审批、快照、停止和验证规则保留在 SOP。
- 适用条件：开发者通过对话进行 Vibe Coding，但项目仍需要可审计、可恢复的 Agent 工作。
- 限制：口语化不能被解释为无限授权；高风险变更仍需正式方案和明确批准。
- 建议 action：vHarness 模板将“开发者输入”和“Agent 内部工程流程”分层设计，并为会话生命周期提供独立提示词。

## EXP-003：迁移执行验证之后仍需宿主语义验收

- 来源：一次 Host Repository 首次接入复盘。
- 通用问题：源文件哈希、目标哈希和 action 全部验证通过，只能证明 Migration Plan 被一致执行，不能证明模板状态、文档 scope、项目规则和验证器已经适合宿主项目。
- 可复用做法：Migration Run verify 后单独执行宿主语义审计，检查项目身份、真实 current state、架构边界、文档 scope、版本管理规则、Project Content 保护和宿主原有验证命令。
- 适用条件：通用框架首次接入或旧版修复完成后。
- 限制：语义审计需要理解宿主项目，不能只依赖框架源文件清单。
- 建议 action：将“执行一致性”和“宿主可用性”设为两个独立验收阶段。

## EXP-004：验证器必须具备 Host Repository 边界

- 来源：一次通用验证器接入业务仓库的复盘。
- 通用问题：面向框架源码仓库的验证器可能要求宿主具备发布目录、扫描所有业务 Markdown、把生成目录视为源码，或把 URL 片段误判为盘符路径。
- 可复用做法：验证器提供 host profile，只扫描 Framework Infrastructure 与 Developer Resources；Project Content 保持项目原有规则；排除标准生成目录，并为合法 URL、真实绝对路径和业务目录隔离建立回归测试。
- 适用条件：同一套治理工具同时用于框架源码、发布模板和 Host Repository。
- 限制：生成目录和项目内容边界需要结合技术栈配置，不能无限扩大排除集。
- 建议 action：所有框架验证器显式声明 profile、受管根和排除理由。

## EXP-005：治理记录也要最小化外部路径

- 来源：一次附件驱动的方案编写与架构验证复盘。
- 通用问题：为了记录来源而写入开发者机器上的完整附件路径，会泄露环境结构并触发绝对路径门禁。
- 可复用做法：治理文档只保留来源角色、必要文件名、内容摘要和可复核的项目内证据；确需定位外部资源时由当前会话传入，不固化盘符或用户目录。
- 适用条件：方案、复盘或手册引用下载目录、用户目录、临时挂载或外部工作区资料。
- 限制：受监管审计如果要求精确外部来源，应使用专门的受控 provenance 机制，而不是普通项目文档。
- 建议 action：文档门禁同时扫描治理文件中的真实本地绝对路径。

## EXP-006：方案修订需要全局决策一致性检查

- 来源：一次多轮范围增补和开发者排除场景的复盘。
- 通用问题：局部修改 Decision Item 后，旧目标、验收标准或另一条 Decision Item 可能继续表达相反 action，形成表面已批准但内部冲突的方案。
- 可复用做法：每次方案增补后，按相关术语全局检查事实基线、目标、文件清单、阶段、验收和全部 Decision Item；后续决定保留为 `superseded -> preserve/adopt/merge/relocate/defer` 轨迹，不直接抹去历史。
- 适用条件：方案经过两轮以上范围修改、排除项变化或审批增补。
- 限制：文本搜索只能发现已知术语，仍需要语义复核。
- 建议 action：正式方案验证增加 action 冲突与遗漏范围检查。

## EXP-007：整文件重写采用小批次并立即验证

- 来源：一次多文档整文件重写的复盘。
- 通用问题：编辑工具可能不支持在单次补丁中对同一文件先删除再新增；长文本生成也可能引入异常字符、缺失引用或重复逻辑 ID。
- 可复用做法：先确认编辑工具能力；整文件重写拆成可恢复的小批次；每批完成后检查文件存在、UTF-8、空字符、Unicode replacement character、内部引用、逻辑 ID 和结构门禁。
- 适用条件：长 Markdown、配置或源码文件需要整体替换。
- 限制：机械检查不能替代内容语义审查。
- 建议 action：把写后快速检查放在长文档生成与批量编辑的阶段门禁中。

## EXP-008：移植版本库元数据后先证明身份与可移植性

- 来源：一次丢失版本库元数据后的本地恢复复盘。
- 通用问题：复制 `.git` 可以恢复历史和索引，但也可能带入错误仓库身份、remote、worktree 指针、对象替代目录、子模块或大文件存储的本地依赖。
- 可复用做法：写入前只读确认项目根、分支、HEAD、remote、对象连通性，以及 alternates、commondir、linked worktrees、submodule 和大文件存储配置；再决定当前工作树相对恢复基线的处理 action。
- 适用条件：工作树仍在，但版本库元数据丢失并从另一同步副本恢复。
- 限制：检查通过只证明元数据可用，不证明当前工作树内容应全部提交，也不授权远端同步。
- 建议 action：把 Git 身份、完整性和路径依赖审计加入工作区恢复流程。

## EXP-009：行尾状态噪音必须与真实内容差异分离

- 来源：一次 Windows 工作树建立本地基线的复盘。
- 通用问题：自动行尾转换可能让大量 tracked 文件显示 modified，即使有效内容只改变了少量文件；按状态数量判断会导致误审或不必要的全仓规范化。
- 可复用做法：结合忽略行尾差异的 diff、暂存后的规范化结果和最终 clean status 判断；是否引入 attributes 或全仓换行提交作为独立 Decision Item。
- 适用条件：跨平台仓库、复制工作树或启用自动行尾转换的环境。
- 限制：忽略行尾差异只适合诊断，不能掩盖真正依赖行尾格式的脚本或生成协议。
- 建议 action：版本库恢复和批量提交 SOP 明确区分内容差异、工作树编码转换和规范化迁移。

## EXP-010：治理方案应在请求批准前通过自身门禁

- 来源：一次正式方案在获批后连续触发元数据与路径验证的复盘。
- 通用问题：如果方案直到实施阶段才验证 Frontmatter、逻辑 ID、scope、路径和格式，开发者可能批准一个本身不可执行的文档，随后被迫重复停止和确认。
- 可复用做法：方案采用标准注册状态；请求批准前运行文档、架构和 whitespace 预验证；预验证通过后再展示范围与 Decision Item。
- 适用条件：项目以受管 Markdown、schema 或验证器约束正式方案。
- 限制：文档预验证不能替代开发者批准，也不能证明实施结果正确。
- 建议 action：把“draft -> 预验证 -> approve -> in_progress -> verified”固化为正式方案生命周期。

## EXP-011：本地基线提交采用暂存前后双阶段安全门禁

- 来源：一次将既有工作树纳入本地版本控制的复盘。
- 通用问题：只检查工作区可能遗漏 ignore 例外、行尾规范化或暂存选择造成的变化；只检查 staged diff 又可能错过被过宽规则隐藏的内容。
- 可复用做法：暂存前检查 tracked、untracked、ignored、秘密、本地路径和文件大小；暂存后检查文件清单、统计、whitespace 和禁入目录；提交后确认 clean status 与本地 ahead 状态。
- 适用条件：首次建立基线、恢复索引、批量纳入治理文件或大量本地文件。
- 限制：模式扫描不能证明完全没有秘密，仍需结合项目的数据目录和人工审查。
- 建议 action：将双阶段门禁作为本地提交的默认高风险验收，并把 push 作为独立授权。
