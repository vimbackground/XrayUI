# XrayUI Vibe Coding 提示词集

这里的每段提示词都可以原样复制到 Agent 对话窗口，不需要先改内容，也不需要懂代码。Agent 会先查看项目，再用容易回答的问题和你聊清楚需求、效果、限制和完成标准。

你只要选择最接近当前情况的一条。技术检查、文件范围、方案、快照和验证由 Agent 按对应 SOP 负责；需要你做决定时，Agent 应用白话说明选择及影响。

## 一、开始或继续开发

### 1. 我有一个新想法

```text
我想为 XrayUI 做一个新功能或改进，但现在只有大概想法。请先读取项目规则、当前状态和相关 SOP，再和我进行简短、口语化的沟通。一次只问我少量关键问题，优先给出容易理解的选项或例子，帮我逐步说清楚想解决的问题、希望看到的效果、不能破坏的内容以及怎样算完成。能从项目中查到的技术信息请你自己检查，不要反过来问我文件、类名或命令。需求明确后，判断是可以直接做，还是需要先写正式方案等我批准；按 `_Dev/SOP/SOP_task_execution_and_verification.md` 和 `_Dev/SOP/SOP_change_planning.md` 执行。
```

### 2. 继续上次正常结束的任务

```text
我想继续上次在 XrayUI 中没有做完的任务。请按照 `_Dev/SOP/SOP_session_handoff.md` 读取项目规则、当前状态、Work Item Registry 和相关方案，核对记录与实际文件。先用几句话告诉我上次做到哪里、已经确认了什么、还剩什么，以及你建议现在从哪一步继续。如果有记录不一致或不确定的地方，先用容易理解的问题问我，不要直接修改。等我们对齐后，再按原来的批准范围继续，并完成相应验证。
```

### 3. 做一个小调整

```text
我想对 XrayUI 做一个比较小的调整。请先查看项目和相关内容，然后用口语化方式问我想改成什么样、什么行为必须保留、我看到什么结果才算满意。不要要求我提供技术文件名或测试命令。按照 `_Dev/SOP/SOP_task_execution_and_verification.md` 判断是否确实属于低风险小改动；如果实际影响比我想象的大，请先解释原因并转为正式方案，不要擅自扩大范围。完成后用白话告诉我改了什么、现在怎么用、验证是否通过。
```

## 二、规划和实施较大的工作

### 4. 先帮我把复杂想法规划清楚

```text
我有一个可能比较复杂的想法。请先不要改代码，按照 `_Dev/SOP/SOP_change_planning.md` 查看项目现状，并通过简短对话帮我把目标、期望效果、不能影响的内容和验收方式确认清楚。技术范围和风险请你自己分析，再用白话解释给我。确认后在 `_System/reviews/` 创建正式方案，清楚列出准备新增、修改或删除什么、分几步做、怎样验证、失败如何恢复、还有哪些事情需要我决定。方案写好后停止，等我明确批准再实施。
```

### 5. 执行我已经批准的方案

```text
我已经批准了当前任务的正式方案。请先找到并重新读取该方案以及项目当前状态，用白话向我确认你理解的目标和批准范围。然后按照 `_Dev/SOP/SOP_resilience_and_disaster_recovery.md` 创建并验证快照，再严格按方案分阶段实施和验证。不要顺手做方案外的修改；如果发现必须扩大范围、项目状态变化或新的风险，请立即停下来说明，并等我批准方案增补。任何验证失败都要停止，告诉我失败在哪里、已经完成什么以及回滚路径。全部通过后更新方案、当前状态和 Work Item Registry。
```

## 三、问题、检查和验收

### 6. 我遇到了问题，请先查原因

```text
XrayUI 现在有一个问题，但我不确定原因。请按照 `_Dev/SOP/SOP_systematic_debugging.md` 先和我聊清楚我看到了什么、原本希望怎样、问题大概在什么时候出现。一次只问少量容易回答的问题，不要要求我先提供日志、代码位置或根因。之后请你自己检查项目、尝试安全复现并收集证据。先只做诊断，不修改文件或系统状态；用白话告诉我问题是什么、为什么发生、影响多大，以及你建议怎样修。需要修复时，再说明是否必须先写正式方案。
```

### 7. 修复已经确认的问题

```text
请继续修复我们刚才已经确认的问题。先按照 `_Dev/SOP/SOP_systematic_debugging.md` 复核根因和允许修改的范围，再判断是否需要正式方案或快照；需要时必须先停下来等我批准。请做解决根因的最小修改，并增加能防止问题再次出现的验证。完成后先用白话告诉我问题是否已经解决、我需要怎样确认，再列出测试结果和仍然存在的限制。任何验证失败都要立即停止，不要通过关闭检查或忽略错误来假装完成。
```

### 8. 只看看项目现在是什么状态

```text
请先不要修改任何文件。我想知道 XrayUI 现在实际做到哪里、记录和文件是否一致、有没有未完成或有风险的内容。请按照 `_Dev/SOP/SOP_read_only_state_audit.md` 核对项目规则、当前状态、Work Item Registry、相关方案、实际文件、验证记录和必要的 `_wip` 内容。先用白话总结现在是否安全、最重要的差异和建议下一步，再提供必要证据。不要修复、安装、提交、清理或更新状态，等我决定下一步。
```

### 9. 把当前改动完整验证一次

```text
请按照 `_Dev/SOP/SOP_architecture_verification.md` 检查当前改动是否真的完成。验证范围由你根据实际变更、项目 README、CI 和相关 SOP 判断，不要让我选择技术命令。先执行最贴近改动的检查，再执行风险相称的回归验证；如涉及发布或 updater，也要运行对应验证。记录每项检查是否通过、失败、跳过或有警告。最后先用白话告诉我功能是否达到目标、现在能不能继续使用或发布、还有什么没验证，再给出必要的技术证据。失败时立即停止。
```

### 10. 请另做一次独立复核

```text
请按照 `_Dev/SOP/SOP_independent_review.md` 对当前成果做一次独立、只读复核，不要直接修复。请先查看原始需求、批准方案、实际修改和验证结果，重点寻找遗漏、回归、安全风险、边界问题以及验证不足。先用白话告诉我能不能继续使用或发布、最需要担心什么、建议下一步是什么；然后按严重程度列出有证据的问题。没有发现问题时也要说明仍未验证的范围。结论使用 pass、pass_with_follow_up 或 block。
```

### 11. 发布前做最后验收

```text
我准备发布 XrayUI，请先不要修改产品代码。请结合 `_Dev/SOP/SOP_architecture_verification.md`、`_Dev/SOP/SOP_independent_review.md` 和 `_Dev/SOP/SOP_resilience_and_disaster_recovery.md`，主动确认这次准备发布的版本、目标平台和发布方式；能从 README、CI 和项目文件查到的信息请自己检查。运行风险相称的完整验证，检查敏感数据、生成内容、发布产物和回滚路径。任何阻断项失败都立即停止。最后用白话明确告诉我现在是否适合发布、有哪些警告和下一步，并保留完整验证证据。
```

## 四、会话结束、暂停和恢复

### 12. 今天先正常结束，下次还是用这个 Agent

```text
我今天先做到这里，下次还会使用同一个 Agent 继续。请按照 `_Dev/SOP/SOP_session_handoff.md` 安全结束当前会话：核对实际文件和验证结果，区分已经完成、尚未验证、半成品和未开始内容，更新 current state 与 Work Item Registry，记录快照或回滚路径以及下次唯一明确的第一步。不要开始新的开发。最后用白话告诉我本次完成了什么、有没有没收尾的内容，并给我一句下次可以直接复制使用的继续提示词。
```

### 13. 结束当前会话，并换一个 Agent 工具继续

```text
我准备结束当前会话，并换一个不同的 Agent 工具继续开发。请按照 `_Dev/SOP/SOP_cross_agent_migration.md` 做完整移交：核对文件、方案、验证、半成品、平台限制和恢复路径，更新 current state 与 Work Item Registry，不要开始新修改，也不要假设新 Agent 拥有相同权限。最后用白话总结交接状态，并生成一段可以原样复制给新 Agent 的接管提示词，让它先确认新平台能力、核对实际文件、向我报告接管结果并等待确认后再继续。
```

### 14. 我需要临时暂停开发

```text
我现在需要暂停 XrayUI 的开发，可能过一段时间再回来。请按照 `_Dev/SOP/SOP_development_pause_and_resume.md` 停止开始新工作，安全结束或停住当前最小步骤，核对已经修改的文件和最后验证结果。把准确暂停点、已完成内容、半成品、风险、快照或回滚路径以及回来后的第一步记录到 current state 和 Work Item Registry。不要把未验证内容写成完成。最后用白话告诉我已经安全停在哪里，并给我一句回来时可以直接复制的继续提示词。
```

### 15. 继续之前主动暂停的开发

```text
我现在想继续之前主动暂停的 XrayUI 开发。请按照 `_Dev/SOP/SOP_development_pause_and_resume.md` 读取暂停记录、项目规则、当前状态、Work Item Registry 和相关方案，核对实际文件与记录是否一致。先用几句话告诉我之前为什么暂停、做到哪里、现在最安全的下一步是什么；有差异时先问我，不要直接覆盖或恢复。确认一致后按原批准范围继续，并重新运行必要验证。
```

### 16. 上次意外中断了，请检查后继续

```text
上次开发因为死机、断网、Agent 意外关闭或其他故障中断了，我不确定最后一步是否完成。请按照 `_Dev/SOP/SOP_interruption_recovery.md` 先不要写入，检查项目规则、当前状态、Work Item Registry、相关方案、实际文件、仍在运行的进程以及相关快照和 `_wip` 制品。把内容分成已验证成果、未验证半成品、未知或冲突内容、可以安全重做的步骤。先用白话告诉我中断前可能做到哪里、已经确认什么、还不确定什么和最安全的恢复办法。任何覆盖或实际恢复动作都必须先预演并等我批准。
```

## 五、复盘和持续改进

### 17. 复盘整个会话

```text
请按照 `_Dev/SOP/SOP_retrospective_and_knowledge_distillation.md` 复盘这次完整会话。你先从方案、状态、实际文件、命令和验证结果还原事实，只向我询问无法从项目中确认的感受或取舍。总结这次完成了什么、哪里顺利、哪里踩坑、为什么、怎样修正，以及以后怎样做得更稳。把项目事实和 Harness 改进线索记录到 `_System/memory/retrospective_log.md`；稳定流程用于改进 `_Dev/SOP/`，面向开发者的用法用于改进提示词集；可支持 vHarness 项目的经验必须提炼、脱敏、解耦后记录到 `_Dev/References/agent_assisted_development_experience.md`。不要自动写入外部项目。最后用白话告诉我学到了什么、沉淀到哪里、还有什么需要我决定。
```

### 18. 只复盘某一个任务

```text
请按照 `_Dev/SOP/SOP_retrospective_and_knowledge_distillation.md`，只复盘我刚刚完成或指定的那个任务，不重复分析更早的内容。请从 Work Item、相关方案、修改文件和验证结果中确认事实，再和我简短沟通实际效果是否符合预期。提炼本次新出现的经验、教训、工具用法和限制，分别放入正确的 `_System` 状态/复盘位置与 `_Dev` SOP、manuals 或 References；用于支持 vHarness 项目的内容先提炼、脱敏、解耦，只形成候选经验，不自动对外同步。报告实际更新和证据。
```

## 六、工作区审计和清理

### 19. 检查是否有本地路径或不该提交的内容

```text
请按照 `_Dev/SOP/SOP_workspace_audit_and_cleanup.md`，只读检查 XrayUI 项目中是否存在硬编码本地绝对路径、不可读文本、敏感数据、异常生成内容或边界混放。只检查当前项目和我明确授权的范围，不扫描项目外目录或 `_Dev/box/`。请结合项目运行方式区分真正的源码问题与 bin、obj、target 中正常的工具生成路径。先用白话告诉我发现了什么、影响多大、建议怎样处理，再列出精确证据；本次不要直接批量替换或清理。
```

### 20. 安全检查哪些临时内容可以清理

```text
请按照 `_Dev/SOP/SOP_workspace_audit_and_cleanup.md` 先做只读清理审计，不要立即删除。检查当前项目内的缓存、构建输出、临时文件、旧快照和 Migration Run，区分可以安全重建、仍用于恢复、关联未完成任务、未知来源和建议保留的内容。先用白话分成“可以安全清理”“现在不要动”“需要我决定”三类，并列出精确路径、原因、大小和可恢复性。等待我针对明确目标单独批准后才能执行删除；不得清理最后一份已验证快照、`_Dev/box/` 或项目外内容。
```

## 七、Git 丢失后的本地恢复

### 21. 恢复 Git，并且只更新本地

```text
本项目的 Git 信息曾经丢失，我已经从同一项目的同步副本恢复或准备恢复。请按照 `_Dev/SOP/SOP_workspace_audit_and_cleanup.md` 先只读确认项目根、分支、版本、远端地址、仓库完整性和是否带入其他电脑的路径依赖，再区分真正的文件修改、换行提示、未跟踪内容和应该忽略的本地文件。不要执行 reset、checkout、clean、pull 或 push。需要以当前项目为准建立本地基线时，先按照 `_Dev/SOP/SOP_change_planning.md` 写正式方案并等我批准；获批后建立快照，按照 `_Dev/SOP/SOP_task_execution_and_verification.md` 完成测试、暂存前后安全检查和本地提交。除非我以后单独明确要求，否则任何内容都不要上传到远端。最后用白话告诉我 Git 是否恢复正常、本地提交是什么、还有哪些风险或决定。
```

## 使用原则

- 直接复制最接近当前情况的一条即可，不需要先编辑。
- 如果你不知道选哪条，就使用“我有一个新想法”或“只看看项目现在是什么状态”。
- Agent 应自己读取项目并主动推导技术信息，一次只问少量必要问题。
- 口语化沟通不等于无限授权；正式方案、审批、快照、失败停止和验证仍按 SOP 执行。
- SOP 是 source_of_truth。SOP 路径变化或流程更新时，必须同步检查本提示词集。
